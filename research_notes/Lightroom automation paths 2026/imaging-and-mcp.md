# Imaging APIs and official agent connectors

Research date bound: 2026-10-20. Pages below were fetched on that date. Decision these notes support: whether the retired Firefly Lightroom API, Photoshop API v2, Adobe for Creativity MCP, or Zapier’s Lightroom MCP can edit a user’s Lightroom cloud catalog or drive the Lightroom desktop app.

## Firefly Services Lightroom API: end of life, migration target, and endpoint mapping

### Takeaway
Adobe’s deprecation page sets Lightroom API end of life at July 31, 2026 and tells customers to migrate to Photoshop API v2. The published mapping sends the old Lightroom edit endpoints (auto tone, auto straighten, presets, XMP, and the general edit call) to `POST /v2/edit` on `photoshop-api.adobe.io`. Adobe does not publish a Lightroom “convert” endpoint in that table; format conversion is a Photoshop v1 rendition endpoint that moves to `/v2/create-composite`.

### Cited Findings
- The Lightroom API “will reach end-of-life (EoL) on July 31, 2026.” Customers are told to migrate to Photoshop API v2. The FAQ repeats “End of Life (EOL): July 31, 2026” and “Migrate to Photoshop API v2 before August of 2026.” The stated reason is that Adobe is consolidating imaging API capabilities into Photoshop API v2. Help is directed to the customer’s Adobe Customer Success Manager and Support Team. — [Deprecation announcement](https://developer.adobe.com/firefly-services/docs/lightroom/getting-started/deprecation-announcement/)
- The same July 31, 2026 date is also the published end of life for Photoshop API v1: “Photoshop API v1 will reach end of life on July 31, 2026.” — [Photoshop API overview](https://developer.adobe.com/firefly-services/docs/photoshop/)
- Migration overview: “This overview helps you understand the general changes and how to prepare for the migration from the legacy v1 Photoshop and Lightroom APIs to the new unified v2 API.” Photoshop API v2 uses `photoshop-api*.adobe.io` instead of `image*.adobe.io`. — [Migration to v2 overview](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/)
- Production base URLs in the behavior catalog: v1 `https://image.adobe.io`, v2 `https://photoshop-api.adobe.io`. — [V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog)
- Adobe’s service migration reference table, quoted from the overview (v1 endpoint, v2 endpoint, guide):
  - `/lrService/autoTone` → `/v2/edit` — Edit Operations
  - `/lrService/autoStraighten` → `/v2/edit` — Edit Operations
  - `/lrService/presets` → `/v2/edit` — Edit Operations
  - `/lrService/xmp` → `/v2/edit` — Edit Operations
  - `/lrService/edit` → `/v2/edit` — Edit Operations
  - `/lrService/status/{jobId}` → `/v2/status/{jobId}` — Status Migration
  - `/pie/psdService/renditionCreate` → `/v2/create-composite` — Format Conversion
  - The same table also maps Photoshop document, action, artboard, and manifest endpoints; those are not Lightroom edit calls. — [Migration to v2 overview](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/)
- The LLM migration reference repeats that Lightroom mapping and describes each row: auto tone adjustment, auto straighten image, apply Lightroom presets, apply XMP metadata, manual adjustments. Its decision tree says “Convert PSD to JPEG/PNG/TIFF without edits” uses `/v2/create-composite` with no edits block, and labels v1 `/pie/psdService/renditionCreate` as “Convert PSD to other formats.” It also says “If using format conversion: `/renditionCreate` → `/v2/create-composite` (no edits).” — [LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)
- Edit Operations Migration consolidates the same five Lightroom endpoints onto `/v2/edit` and shows the parameter form: `autoTone: true`, an `autoStraighten` object, a `presets` array, an `xmp` object, and adjustment parameters. The v2 auto-tone example is `POST https://photoshop-api.adobe.io/v2/edit` with `image.source.url` set to `<SIGNED_GET_URL>`, `edits.autoTone: true`, and `outputs[].destination.url` set to `<SIGNED_POST_URL>`. The v1 example posts to `https://image.adobe.io/lrService/autoTone` with `inputs.href` `<SIGNED_GET_URL>` and `outputs[].href` `<SIGNED_POST_URL>`. — [Edit operations migration](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/edit-operations)
- The still-published v1 Apply Edits guide describes `/lrService/edit` as programmatic control of “the same adjustments you would make manually in the Lightroom Edit Panel,” and its request example uses `<SIGNED_GET_URL>` / `<SIGNED_POST_URL>` against `https://image.adobe.io/lrService/edit`. It does not describe a catalog id, album id, or a desktop app command. — [Apply Lightroom API edits](https://developer.adobe.com/firefly-services/docs/lightroom/guides/apply-edits/)
- Behavior catalog, edit group: v1 endpoints were one call per operation; v2 `/v2/edit` can combine `autoTone`, `autoStraighten`, `light`, `color`, `detail`, `effects`, `optics`, and XMP presets. Input moves from `inputs[0].href` plus `"storage": "external"` to `image.source.url`. Output moves from `outputs[0].href` to `outputs[0].destination.url`. Authentication for this group is “OAuth Server-to-Server” on both v1 and v2. — [V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog)
- Two Adobe pages disagree on where v2 adjustment fields sit. The behavior catalog says adjustment parameters move from the v1 `options` block to “Top-level fields (`autoTone`, `light`, `color`, etc.).” The Edit Operations guide and the LLM reference put those fields inside an `edits` object (for example `"edits": { "autoTone": true }`). — [V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog); contradicted by [Edit operations migration](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/edit-operations) and [LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)
- The behavior-catalog checklist says “All `/lrService/*` calls → `/v2/edit`.” The Edit Operations page contradicts a literal reading of that line. It lists Lightroom v1 endpoints with no direct v2 migration path: `/lrService/mask` (“Deprecated and removed as a standalone endpoint”; “Mask functionality is now available through the XMP feature in `/v2/edit`”), `/lrService/predict` (“Deprecated and removed”), `/lrService/depthRefinement` (“Deprecated”; “Feature no longer supported”), `/lrService/index` (“Removed”; “No v2 equivalent available”), and `/lrService/xmpToPreset` (“To be implemented”; “V2 equivalent is planned for a future release”). — [V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog); contradicted in part by [Edit operations migration](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/edit-operations)
- A second Adobe contradiction on `/lrService/mask`: the Edit Operations page says that endpoint’s mask functionality moved into `edits.xmp.masks` on `/v2/edit`. The LLM reference says “The V1 `/lrService/mask` endpoint is a separate, unrelated feature for AI-based mask generation (selectSubject, selectSky, etc.) and has a different deprecation path,” and that the XMP mask files are localized Camera Raw adjustments, not that AI mask endpoint. — [Edit operations migration](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/edit-operations); contradicted by [LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)
- No row in the published v1-to-v2 tables is named convert under `/lrService`. The conversion row Adobe does publish is Photoshop’s `/pie/psdService/renditionCreate` → `/v2/create-composite`. — [Migration to v2 overview](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/); [LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)

### Inferences
- The old Firefly Lightroom API, as Adobe documents the request shape, processes an image the caller supplies by URL (or another storage reference) and writes an output file. That is an imaging-service contract. It is not, on these pages, a catalog or desktop-app contract.
- “Convert” in this product family is the Photoshop rendition/format-conversion path, not one of the five Lightroom edit endpoints. Zapier’s separate “Convert File” action is not identified on these Adobe pages.

### Gaps
- The deprecation page, fetched for a 2026-10-20 bound, still says the API “will reach” end of life on July 31, 2026 and still says to migrate “before August of 2026.” These notes do not establish whether Adobe has actually stopped serving `image.adobe.io` Lightroom routes after that date.
- Adobe publishes no single page that uses the word “convert” as a Lightroom v1 route. If an older Lightroom convert route existed under another name, it was not in the mapping tables fetched here.
- The `/lrService/mask` deprecation path is inconsistent across two current Adobe guides, so these notes do not pick one.

## Photoshop API v2: catalog versus image files, and authentication

### Takeaway
Photoshop API v2 processes image and PSD inputs addressed by URL or a storage reference and writes outputs to a destination URL or other storage. Adobe documents authentication as OAuth server-to-server client credentials. These pages do not say the API edits a Lightroom catalog or drives the Lightroom desktop app.

### Cited Findings
- Unified v2 surface from the migration overview: “All Photoshop and Lightroom operations are now served from a single, unified API.” Lightroom operations are grouped as “Edit Operations - Lightroom editing operations (autoTone, presets, XMP, etc.).” — [Migration to v2 overview](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/)
- Inputs and outputs are file locations. Behavior catalog storage table: presigned URL (S3) is `{"url": "..."}`; Azure Blob and Dropbox are also URL destinations; Creative Cloud is `{"creativeCloudPath": "..."}` or `{"creativeCloudFileId": "..."}`; hosted Adobe-managed storage is `{"validityPeriod": N}` with N from 60 to 86400 seconds; embedded is base64, string, or json. The v1 AWS `storage` field is deprecated in favor of the presigned URL pattern. — [V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog)
- The LLM reference’s four storage options are external presigned URLs, Creative Cloud storage, embedded storage, and hosted temporary storage. It adds: “Creative Cloud Storage refers specifically to ACP (Adobe Content Platform) for file storage and access.” — [LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)
- Edit examples use signed URLs, not a catalog record. Auto tone v2 body fields are `image.source.url` = `<SIGNED_GET_URL>` and `outputs[].destination.url` = `<SIGNED_POST_URL>`, with `mediaType`. — [Edit operations migration](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/edit-operations)
- Authentication, migration overview: “Authentication remains unchanged. Continue using your existing OAuth Server-to-Server credentials with the new v2 endpoints.” — [Migration to v2 overview](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/)
- Authentication, LLM reference: “V2 uses the same OAuth Server-to-Server authentication as V1.” The documented token call is `POST https://ims-na1.adobelogin.com/ims/token/v3` with `grant_type=client_credentials`, `client_id`, `client_secret`, and `scope=openid,AdobeID,read_organizations`. Example API calls send `Authorization: Bearer $token` and `x-api-key`. — [LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)
- The behavior catalog repeats “Authentication OAuth Server-to-Server (unchanged)” for edit operations and “Authentication is unchanged between V1 and V2. Continue using your existing OAuth Server-to-Server credentials.” — [V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog)
- `lightroomPath` appears only as one allowed image source reference, alongside `url`, `creativeCloudPath`, and `creativeCloudFileId`, in the artboard section: “Input structure: V1 `inputs[].href` → V2 `images[].source.url` (or `creativeCloudPath`, `creativeCloudFileId`, `lightroomPath`).” Source options listed there: “External URL, Creative Cloud Path, Creative Cloud File ID, Lightroom Path.” The artboard checklist repeats that each image source may be `url`, `creativeCloudPath`, `creativeCloudFileId`, or `lightroomPath`. The page does not define what a Lightroom path points at, and it does not say this writes a catalog, an album, or the desktop app. — [LLM migration reference](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/llm-migration-reference)
- Job results are output destinations. `/v2/status/{jobId}` returns `status` (`not_started`, `running`, `succeeded`, `failed`), an `outputs` array with destination URLs, and an `errors` array. — [V2 API behavior catalog](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/v2-api-catalog)

### Inferences
- Server-to-server client-credentials auth is a developer-project credential. It is not the user Lightroom OAuth flow a cloud-catalog API would use to act as the signed-in photographer. Combined with signed-URL inputs, the documented contract is file processing.
- `lightroomPath` is a source locator on an artboard request. These notes do not treat it as catalog editing, because the source never says that.

### Gaps
- Adobe does not, on the pages fetched, define the syntax or the backend of `lightroomPath` beyond naming it as an artboard image source. Whether that string can address a cloud photo was not stated.
- No fetched Photoshop API v2 page says “this does not edit a Lightroom catalog.” The negative claim is an absence of any catalog write, album write, or desktop-control operation in the endpoint maps and request examples above.

## Adobe for Creativity MCP: endpoint, hosts, tools, and Lightroom scope

### Takeaway
Adobe’s own plugin manifest sets the connector URL to `https://adobe-creativity.adobe.io/mcp`. Adobe says it is a Claude connector with 50+ tools across several Creative Cloud apps, including Lightroom, and that guests get about 40 tools. Adobe does not publish the MCP tool names or their input schemas on the pages or in the manifest fetched here, and no Adobe page fetched says a tool reads or writes a Lightroom catalog, album, or the installed desktop app.

### Cited Findings
- Adobe’s plugin manifest for this connector contains only an HTTP MCP server named “Adobe” at `https://adobe-creativity.adobe.io/mcp`. It does not list tools. — [adobe/skills `.mcp.json`](https://raw.githubusercontent.com/adobe/skills/main/plugins/creative-cloud/adobe-for-creativity/.mcp.json)
- Product page: “Access 50+ tools across Photoshop, Lightroom, Illustrator, Firefly, Premiere, Express, InDesign, and Adobe Stock — all through natural language, without switching apps.” “Sign in with your Adobe account for higher usage limits, more tools, and cross-session continuity.” Hosts: “Claude chat (web & mobile), Cowork (desktop), Claude Desktop.” “Guest users can use free tools included in this MCP right away (about ~40 standard tools), directly in chat. Sign in with a free or paid Adobe account when you want more tools, Creative Cloud storage for your assets, higher usage limits, and continuity across sessions.” Mobile note: new connectors and skills cannot be browsed or installed from iOS or Android; set up on web or desktop first. “Continue in Adobe apps” says you can batch edit photos and send them to Firefly Boards, continue a template in Express, or “download your assets and pick up where you left off in any Adobe app.” — [Adobe for Creativity](https://developer.adobe.com/adobe-for-creativity/)
- Getting started repeats setup in Claude chat, Claude Desktop, or Cowork. Connector install path is Claude → Customize → Connectors → browse “Adobe for creativity.” Signing in is optional; skipping it continues as a guest “with reduced capabilities.” The plugin requires the connector and “Only users with access to paid Claude plans would be able to install Plugins.” Skills can be uploaded from the Adobe skills GitHub repository. Platform table: Claude on the web, Claude Desktop (macOS, Windows), and Cowork (macOS, Windows, paid Claude plans only) are supported; mobile apps can run workflows already installed but cannot install new connectors, skills, or plugins. — [Getting started](https://developer.adobe.com/adobe-for-creativity/getting-started/)
- FAQ: “No, many Adobe tools are available without signing in. More tools are available when you sign in, including Gen Expand and video tools. A few tools require paid subscription.” The FAQ repeats the “50+ tools” list of apps, including Lightroom, “without switching apps.” Any Claude plan can use the connector; Cowork and plugins need a paid Claude plan (Pro, Max, Team, or Enterprise). Connector versus skills versus plugin: “The connector is the bridge that lets Claude call Adobe’s tools. Skills teach Claude how to do specific creative workflows well. The plugin (Cowork only) bundles the connector, skills, and slash commands together.” — [FAQ and support](https://developer.adobe.com/adobe-for-creativity/support/)
- April 28, 2026 Adobe blog: the connector “orchestrating multi-step workflows across Creative Cloud apps, drawing on pro-grade tools from Photoshop, Illustrator, Firefly, Express, Premiere, Lightroom, InDesign and Stock” and does that “right inside Claude.” Signing in “unlocks higher usage limits, more tools, and work that saves across sessions.” The post says the connector is “available globally for Claude starting today.” — [Adobe blog, 2026-04-28](https://blog.adobe.com/en/publish/2026/04/28/adobe-for-creativity-connector)
- Adobe publishes skill names, not an MCP `tools/list`. The `adobe/skills` README section “Adobe for Creativity (for Claude desktop app only)” lists: `adobe` (“A one-glance orientation to the Adobe for creativity connector”); `adobe-batch-edit-photos` (“Apply consistent, cohesive photo adjustments across a set of images — matched tones, presets, and cinematic looks”); `adobe-create-pdfs-from-data` (InDesign data merge from CSV/TSV and an INDD template); `adobe-create-social-variations` (platform-ready image and video crops); `adobe-design-from-template` (Express templates); `adobe-edit-quick-cut` (video sizzle or highlight reel); `adobe-retouch-portraits` (“Bulk walk-away retouching for wedding and event portraits: auto-straighten, auto-tone, and auto-light across a folder”); `adobe-resize-photos-and-videos` (exact pixel dimensions, aspect ratios, or named sizes). The README does not say these skills read or write a Lightroom catalog, album, or desktop app. The same README’s Creativity section is scoped “for Claude desktop app only,” which is narrower than the developer site’s web and Cowork hosts. — [adobe/skills README](https://github.com/adobe/skills/)
- Prompts page, photo-related skills, with the inputs the page actually names: portrait retouch takes “headshots” and can include “balanced lighting, background blur, auto-straighten, and a portrait crop”; example prompt “Use portrait refinement to edit these headshots.” Batch edit applies “consistent adjustments across a set of images”; example “Batch edit these photos — make them warm, consistent, and cinematic.” The same page marks “Require Adobe ID to use” on design-from-template, resize-videos, quick-cut, and create-social-variations. It does not put that line on the portrait or batch-edit blurbs in the fetched text. — [Prompts and workflows](https://developer.adobe.com/adobe-for-creativity/prompts-and-workflows/)
- None of the Adobe pages above names an MCP tool whose input is a Lightroom catalog, album, or the installed desktop app. Photo examples are described as dropped-in images, headshots, a set of images, or a folder.

### Inferences
- What Adobe verifies is a hosted MCP endpoint plus a count of tools and a set of workflow skills. The photo skills are described as operating on images the user supplies (a set, headshots, a folder), then optionally handing work off by download or by sending it to Firefly Boards or Express. That is not a documented catalog write and not documented control of the Lightroom desktop UI.
- The README’s “Claude desktop app only” line and the developer site’s web/Cowork availability can both be true if they describe different install surfaces (skills plugin versus the connector). These notes do not collapse them into one host list.

### Gaps
- Adobe did not publish a `tools/list` payload, tool JSON schemas, or per-tool input fields in the manifest or on the developer pages fetched here. Individual MCP tool names cannot be verified from Adobe primary sources in this pass.
- Third-party MCP directories (including integrations.sh, mcp.so, and an MCP app-store page) were not used as confirmed tool inventories. One of those pages names Lightroom-scoped tools such as asset search. Those names are unverified against Adobe and are not treated as facts here.
- Guest versus signed-in is documented only as counts and categories (“about ~40 standard tools,” more tools after sign-in, Gen Expand and video tools after sign-in, a few tools need a paid subscription). The exact tool-by-tool split was not published on the pages fetched.
- No Adobe page fetched says whether any Creativity tool can see Lightroom cloud albums. Absence is not a denial; it is undocumented in these sources.

## Zapier Adobe Photoshop Lightroom MCP: 2026 tools and which API they use

### Takeaway
Zapier’s Lightroom MCP page, fetched for this 2026-10-20 pass, advertises five file actions: Apply AutoTone, Apply Presets, Convert File, and two job-status checks. Neither that page nor the Adobe pages above says those actions use the Lightroom catalog API or the imaging API.

### Cited Findings
- Zapier’s MCP page overview sentence: “Adobe Photoshop Lightroom is the cloud-based service that gives you everything you need to edit, organize, store, and share your photos across any device.” The page does not name an Adobe API, a catalog, or the desktop app in the action definitions. — [Zapier Adobe Photoshop Lightroom MCP](https://zapier.com/mcp/adobe-photoshop-lightroom)
- Supported actions and inputs on that page:
  - Apply AutoTone — “Apply Autotone to files.” Inputs: Input File Storage (required), Input File Location (required), Output File Storage (optional), Output File Location (required), Output File Type (optional), Overwrite (optional).
  - Apply Presets — “Apply predefined presets to files.” Inputs: Input File Storage (required), Input File Location (required), Presets File Storage (optional), Presets File Location (required), Output File Storage (optional), Output File Location (required), Output File Type (optional), Overwrite (optional).
  - Convert File — “Convert files in different file formats.” Inputs: Input File Storage (required), Input File Location (required), Output File Type (required), Output File Storage (required), Output File Location (required), Trim To Canvas (optional).
  - Check Status of Autotone or Presets Job — “Check status of an apply autotone or an apply preset job.” Input: Job ID (required).
  - Check Status of File Conversion Job — “Check status of a file conversion job.” Input: Job ID (required).
  - Setup line on the same page: MCP server `mcp.zapier.com`. — [Zapier Adobe Photoshop Lightroom MCP](https://zapier.com/mcp/adobe-photoshop-lightroom)
- Zapier’s integrations page, in the search snippet retrieved the same day, lists the same action names and the same file-storage, file-location, preset-file, output-type, overwrite, trim-to-canvas, and job-id fields, and shows Zaps that start from new files in Dropbox, OneDrive, or Google Drive. The snippet does not say catalog API or imaging API. — [Zapier Lightroom integrations](https://zapier.com/apps/adobe-photoshop-lightroom/integrations)
- Adobe’s deprecation and v2 migration pages do not mention Zapier. — [Deprecation announcement](https://developer.adobe.com/firefly-services/docs/lightroom/getting-started/deprecation-announcement/); [Migration to v2 overview](https://developer.adobe.com/firefly-services/docs/photoshop/guides/photoshop-v2/v1-to-v2/)

### Inferences
- None. The action inputs are files, presets files, output locations, and job ids, but the assignment forbids inferring that those fields mean the imaging API or the catalog API when the source does not say so.

### Gaps
- Zapier does not state which Adobe backend these five actions call. Adobe does not document this Zapier connector on the pages fetched. The backend is therefore unknown from primary statements.
- The Zapier page does not say whether these actions still function after the July 31, 2026 Lightroom API end-of-life date.
- The integrations page was not fetched in full; the field list above for that URL rests on the search snippet, which matched the fully fetched MCP page.

## Community Classic MCP: Automaat/lightroom-mcp

### Takeaway
Automaat/lightroom-mcp, in its own README, targets the Lightroom Classic desktop app and that app’s catalog through a local plugin. It is not an Adobe cloud imaging API.

### Cited Findings
- The project README title is “Lightroom Classic MCP Server.” It says it “Lets Claude (and other AI assistants) talk to your Adobe Lightroom Classic photo catalog” and “Needs: Lightroom Classic on macOS or Windows.” Install steps tell the user to restart Lightroom Classic, open Plug-in Manager, select Lightroom MCP, and click Start Server. The example prompt is “List all my Lightroom collections,” and the README says Claude will list collections in the catalog. — [Automaat/lightroom-mcp](https://github.com/Automaat/lightroom-mcp)

### Inferences
- This is the one product in this note set whose own docs explicitly say they operate on a Lightroom catalog, and the product they name is Classic, not Lightroom cloud and not Photoshop API v2.

### Gaps
- This pass did not re-verify that the plugin’s current code still matches the README, and it did not survey other GitHub Classic MCP repos.
